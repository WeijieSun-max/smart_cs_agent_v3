# 订单查找与消歧策略 V1

## 1. 查询工具选择

- `retail_find_orders`：首选的候选检索工具。适合近期订单、日期范围、商品关键词、状态过滤和没有订单 ID 的自然语言查询；结果包含商品明细并按购买时间倒序排列。
- `retail_list_orders`：适合无需商品明细的简单订单列表或状态列表，也可作为候选检索不可用时的降级路径。
- `retail_get_order`：已知 `order_id` 时读取订单概要。
- `retail_get_order_detail`：已知 `order_id` 后读取最新订单状态、版本和商品明细；需要精确回答或衔接后续操作时优先使用。

同一事实已有工具结果时不要重复调用；候选唯一但缺少必要详情时再调用 detail。

## 2. 日期语义

工具使用半开区间：

- `start_date` 包含当天，格式 `YYYY-MM-DD`；
- `end_date` 不包含当天，格式 `YYYY-MM-DD`；
- “2026 年 7 月”应转换为 `start_date=2026-07-01`、`end_date=2026-08-01`；
- “昨天”“上个月”“最近三个月”等相对日期必须以本轮 `current_date` 为基准转换；
- 用户只说“最近”且没有严格时间要求时，可以不传日期过滤，由工具按购买时间倒序返回，再展示前 5 笔。

不要从订单号中的数字推断下单日期。

## 3. 商品与状态过滤

- `product_query` 使用用户实际提到的商品名称、SKU 或有辨识度的名称片段，不自行扩展品牌或品类同义词。
- 状态过滤只能使用工具契约允许的结构化值。
- 用户问“买过什么”而非某种商品时，不传空泛商品词。
- 用户没有指定状态时，不默认排除取消订单；回答中清楚标注各自状态。

## 4. 结果判定

### list

用户明确要订单历史或列表。即使有多笔结果也直接按时间倒序列出，默认最多 5 笔。

### resolved

满足任一条件：

- 用户提供的 `order_id` 已由 detail 工具验证；
- 日期、商品、状态组合只返回一个候选；
- 用户从上一轮展示的候选中明确选择一笔，且本轮工具复核仍能唯一对应。

### multiple

用户的问题必须落到一笔订单，但当前条件返回多笔。展示最多 5 个候选并询问选择，不替用户猜测。

### not_found

工具返回空结果。说明已应用条件，建议补充订单日期、商品名称、状态、订单号或订单 ID 中最有区分度的一项。

## 5. 候选展示

每个候选只展示工具实际返回且有助于选择的字段：

- 订单号和订单 ID；
- 下单日期；
- 主要商品及数量；
- 状态；
- 总金额与币种。

不要展示内部版本号，除非后续写流程需要；不要输出支付令牌、密文、其他用户信息或未要求的地址快照。

## 6. 状态表达

建议格式：`中文说明（原始状态）`。常见映射：

- `pending`：待处理；
- `processed`：处理中；
- `paid`：已支付；
- `shipped`：已发货；
- `delivered`：已完成/已送达；
- `cancelled`：已取消；
- `return_requested`：已申请退货；
- `exchange_requested`：已申请换货。

未知状态保留原值并使用中性描述，不自行判断终态。

## 7. 与写操作衔接

这个 Skill 不授权写操作。用户随后要求取消、改址、退货或换货时：

1. 传递已解析的 `order_id`，不要仅传候选序号；
2. 对应写能力重新调用订单详情工具，取得最新状态和版本；
3. 验证当前状态是否允许操作；
4. 展示影响并生成待确认提案；
5. 只有用户在新的确认轮次明确同意后才能执行。

历史中的“确认”“就这笔”等表达不能代替当前确认。
